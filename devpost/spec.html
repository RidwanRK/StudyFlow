StudyFlow — Technical Spec

The blueprint for how StudyFlow is built: two programs and a database, with Gemini as the planner and ordinary code as its checker. Markdown (spec.md) is the full version; this page is the quick-to-digest view.

How this works, in plain language

The website

Next.js

What the student sees on phone or desktop. Login, hours, courses, the plan, check-in, replan. It stores nothing important. It shows what the server says.

The server

Express on Node

Accounts, saving, the "do the hours fit?" arithmetic, calling Gemini, and checking Gemini's answer. Your API key lives only here.

The database

MongoDB

Keeps the account, study hours, courses and topics, and the plan, so tomorrow it is all still there.

The planner

Gemini

Gets the topics, deadlines and hours. Returns a timetable as data, and for a replan, a short reason for each move.

"My server adds up whether it fits, asks Gemini to lay out the days, double-checks the answer, and saves it. When a student falls behind, it works out what's left, asks Gemini to reshuffle, shows what moved and why, and lets them accept or reject."

The fit check — plain arithmetic, no AI

Example that fits

Biology exam in 6 days, topics need 10 h. Student has 2 h per day, so 12 h available.

10 h needed / 12 h available → build the plan

Example that doesn't

Same exam, but topics need 15 h against 12 h available.

3 h short → offer "add 0.5 h to each day" (6 days × 0.5 = 3 h) or "add 1.5 h on two days" → or keep my hours (lighter plan)

It checks every exam date, not just the last: all topics due on or before a date must fit in the days before that date. Only after the student answers does the server call Gemini.

Gemini's answer is checked by ordinary code before it is saved. All six must pass, or the server retries once with the errors fed back, then shows a friendly message.

  • The reply has the expected JSON shape.
  • Every date is inside the window (start date to the day before the last exam).
  • No day's total goes over that day's hours.
  • Every block is a multiple of 0.5 h, at least 0.5 h.
  • Every topic exists, and each of its blocks falls before its own course's exam.
  • Each topic's scheduled hours exactly equal the hours it was asked to schedule.

For replans, the server compares old and new schedules to find what really moved, then attaches Gemini's reason to each real move. A reason for something that didn't move is dropped.

  • Gemini slow, failing or invalid → one retry, then "We couldn't build this just now. Your details are saved, so please try again." Nothing bad is ever saved.
  • Gemini rejects the call (key, model access, rate limit) → same friendly message; real error in the server log. Change GEMINI_MODEL.
  • Strange input → Generate disabled until a course has a topic; inline messages for past dates and bad hours.
  • Session expired → back to login.
  • MongoDB unreachable → clear error at startup, so it never fails mid-demo.

Please confirm

Edits trigger a proposal. After the student edits courses, topics, dates or hours, they see the same Accept / Reject screen instead of the plan silently changing. The PRD says the plan "adjusts" and also that replans are accepted or rejected, so I reused the proposal flow. Say so if you want edits to apply automatically.

Other defaults I chose (full list in spec.md > Decisions and Open Issues): plain JavaScript rather than TypeScript, overrides by day of the week, "still need more time" adds a 50% buffer, Replan can also hit the Can't-fit panel, a rejected replan leaves the day open.

Check early in the build: the Gemini structured-output options for Node, that gemini-3.6-flash works with your key, and that your MongoDB allows your IP.
